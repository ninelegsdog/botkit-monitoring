# ADR 0001: offsite-бэкап на restic поверх SFTP вместо git-репозитория

- Статус: принято
- Дата: 2026-09-27
- Относится к: инцидент #335, этап S0 плана #338

## Контекст

Offsite-бэкап выгружался в приватный git-репозиторий
`ninelegsdog/botkit-backups-offsite` по расписанию `17 1,7,13,19 * * *`.
За 18 дней накоплено 76 коммитов.

Git здесь не может быть хранилищем бэкапов по существу, а не из-за ошибки
конфигурации: **в нём нет удаления данных** (удаление файла не стирает его из
истории), **нет клиентского шифрования**, **нет истечения** (retention), и он
живёт в одном аккаунте с исходным кодом. Полный `clone` заберёт всё, что
когда-либо выгружали, навсегда.

Хуже: push-токен `gho_` лежал на проде в `/home/deploy/.git-token` и **не был
отозван** при ротации 26.09 — он монтировался в контейнер как bind-mount и
прозевал инвентаризацию. Выгрузка молча падала 15 дней, и, поскольку свежесть
offsite никто не проверял, отказ никто не заметил.

## Решение

Два зашифрованных репозитория `restic` на мониторе `31.76.11.198`, транспорт
SFTP поверх SSH:

- `data` — 9 ботов, локальные копии, Redis RDB, 12 `.env`. Retention 14/8/6.
- `monitor` — 6 томов наблюдаемости и их конфигурация. Retention 3/2/2.

Приёмник изолирован: пользователь `botkit-backup` без пароля и login-shell,
`ChrootDirectory /srv/botkit-backup`, `ForceCommand internal-sftp`, ключ с
префиксом `restrict`.

Решения, которые стоили отдельного обдумывания:

1. **Два независимых пароля вместо `age` поверх restic.** Разделение данных и
   секретов дешевле двойного шифрования и убирает файлы ключей с продов.
   Знание одного пароля не открывает второй репозиторий.
2. **Согласованные снимки, а не `cp`.** `sqlite3.backup()` внутри контейнера.
   Плоский `cp` по базе, которую в этот момент пишет приложение, даёт надорванный
   файл. Функция перенесена из удаляемого `pullbackups.sh`, а не потеряна.
3. **Свежесть offsite под метрикой.** `botkit-restic-check.timer` публикует
   `botkit_backup_age_seconds` и `botkit_backup_ok` через textfile-коллектор;
   четыре правила покрывают устаревший снапшот, упавшую проверку, отсутствующую
   метрику и неполный набор снимков БД. Отсутствие этого сигнала и было причиной
   15-дневного тихого отказа.
4. **Пароли без резервной копии — компромисс, названный явно.** Второго
   экземпляра паролей нет нигде. Компрометация прод-хоста не даёт доступа к
   бэкапам без пароля, но потеря пароля равносильна потере бэкапов. Пункт внесён
   в `SECURITY-BASELINE.md` и вынесен владельцу как действие.

## Последствия

- **Хорошо.** Данные зашифрованы и стираемы по retention; репозитории переносимы
  на любое хранилище; offsite под наблюдением; снимки БД согласованы; опасный
  `cp` путь больше не единственный.
- **Плохо.** Бэкапы и наблюдаемость лежат на одном хосте: при его смерти теряются
  и UI, и вторая копия. Облачный бэкап позже. Ещё: 9.3 ГБ диска делятся мониторинг
  и restic, что делает retention обязательным, а не рекомендательным.
- **Миграция.** Репозиторий `botkit-backups-offsite` удалён, токен отозван
  (подтверждено `HTTP 401` от `api.github.com` при положительном контроле).
  Каталог `backups-export` выгружен в репозиторий снапшотом `ef069c9a` до сноса,
  скрипты — в `/root/archive/dead-offsite-20260927-1133.tar.gz`.
- **Порядок соблюдён:** удаление только после `restic check` без ошибок и
  успешного restore-drill с `pragma integrity_check = ok`.

## Что рассматривалось и отвергнуто

| вариант | почему нет |
|---------|------------|
| оставить git, добавить retention скриптом | retention в git не создаётся, история уже неотделима от мусора |
| `restic` + S3/B2 сразу | требует отдельного аккаунта и биллинга; репозитории переносимы, поэтому это не блокирует |
| `restic` + `age` на каждом файле | двойное шифрование и файлы ключей на проде — лишние места для ошибки при нулевой выгоде |
| Age-шифрование всего каталога бэкапов | не решает отсутствие удаления; делает бэкапы нечитаемыми без файла ключа рядом |
| WireGuard вместо SFTP | для конфиденциальности не нужно: SFTP уже на SSH; WG добавится в S3 как defense-in-depth |
