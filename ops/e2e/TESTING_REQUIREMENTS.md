# Требования к E2E-тестированию BotKit

Статус: утверждено владельцем 04.10.2026. Источник фактов — инвентаризация девяти
production-ботов и их production-БД.

Назначение: тест должен доказывать поведение бота, а не только то, что вебхук
вернул 200. Отсюда главное правило — **проверка доставки и проверка ответа это
разные тесты**.

---

## 1. Что считается дефектом

1. `/start` у каждого из девяти ботов даёт приветствие, содержащее ожидаемую строку.
2. Приветствие содержит клавиатуру с кнопками. Нет кнопок — бот «молчит».
3. **`/start` срабатывает при любом состоянии.** После текстовой кнопки, после
   неудачного ввода, при повторе — всегда входной экран.
4. `/start <payload>`: payload разбирается, а не игнорируется молча.
5. Ни одна команда вне белого списка не приводит к изменению данных.
6. `/admin` недоступен не-админу и не меняет состояние.
7. Вебхук отвечает 200 на синтетическом обновлении **без побочных эффектов в БД**.
8. Telegram доставляет апдейт. Проверяется по логам, не по ответу бота.
9. Каждый бот отвечает в пределах `E2E_TIMEOUT` = 30 с.
10. При сбое приходит оповещение. Проверяется отдельным негативным тестом.

шесть ботов, а не ослабляется сценарий.

Текстовые кнопки — источник FSM-ловушек. Нажатие «🔍 Проверить заказ» оставляет
состояние `entering_number`, и следующий текст трактуется как номер заказа. В
production БД `pricesentry` из-за этого лежит товар с именем «📦 Мои товары»:
label кнопки, сохранённый как товар.

## 3. Запрещённые команды

Жёсткий запрет, проверяется в `tests/test_no_payment_scenarios.py` и дополняется:

- `/buy_docs` (docuflow) — инициирует оплату
- `/send` (support) — рассылка всем
- `/admin` у всех девяти — вход в админку
- любые `callback` из групп `adm:` (membership)
- `/delete_my_data` — стирает данные, в тестах недопустим

Текстовые кнопки, переводящие в состояние ожидания ввода — «🔍 Проверить заказ»,
«➕ Добавить», «➕ Новый заказ», «➕ Новый тикет», «📝 Оставить заявку»,
«📄 Создать документ» — в сценариях проверки `/start` использовать нельзя.
Исключение — явный кейс «загрязнённое состояние», который обязан их закрывать.

## 4. Правила сценариев

1. Каждый шаг проверяет ровно один ответ.
2. Пауза между шагами не меньше трёхкратного `rate_limit`. Это защита от тихих
   гонок, а не от известной ошибки: `ThrottlingMiddleware` имеет default 0.5 с.
3. Сценарий обязан завершать состояние, которое сам открыл: либо закрывает FSM,
   либо помечен как «требующий чистки».
4. Каждый бот проверяется независимо, без зависимости от порядка.
5. `expect` — substring из реального текста бота, а не из документации.
6. Платёжных сценариев нет вообще.

## 5. Требования к раннеру

1. `E2E_ALERT_URL` обязателен. Нет адреса — раннер не запускается, а не работает
   молча. Гейт стоит в `main()` до первого обращения к Telegram и завершает
   процесс кодом `2` (`EXIT_NO_ALERT_TRANSPORT`). Код `1` при этом остаётся
   «флот провалился», поэтому в журнале и в `systemctl` видно, что тесты не
   запускались, а не что прошли.
   Сознательный прогон без оповещения — `E2E_ALLOW_NO_ALERT=1`: гейт
   пропускается, но в stderr печатается `WARNING`, и это видно в журнале.
   По умолчанию лазейка выключена.
2. Отчёт по каждому боту: `ok` / `fail`, причина, был ли ответ.
3. Пре-флайт каждого прогона: сессия авторизована, туннель жив, `IMAGE_TAG`
   совпадает с пином, бот в списке ровно один раз.
4. Раннер не отправляет `/start`, пока не проверил авторизацию.
5. Раннер пишет verbosity по каждому апдейту и сработавшему хендлеру. Иначе
   причину провала приходится восстанавливать логами прод-контейнеров.
6. Раннер не имеет доступа к токенам ботов — гейт `tests/test_no_token_reads.py`.

## 6. Требования к оповещениям

1. Канал — Alertmanager v2 API, внутренний порт. Наружу не публикуется.
2. Обязателен Watchdog: тест должен присылать и успешный результат. Иначе
   «Alertmanager жив» и «тест мёртв» неразличимы.
3. Алерты классифицируются: `BotNotAnswering`, `WebhookNotDelivered`,
   `TestRunnerDead`. Один общий «E2E упал» бесполезен: провал одного бота даёт
   ту же тревогу, что падение всей системы.
4. Троттлинг сохраняется, иначе один битый бот пишет каждые 30 с.
5. Известный и сознательно принятый риск: аккаунт теста и аккаунт оповещений
   совпадают. Принимается только на время стенда.

## 7. Безопасность

1. Перед прогоном на проде — снимок БД всех девяти.
2. После прогона — сверка, что число строк в пользовательских таблицах не
   изменилось. Исключение — `audit_log`.
3. Сессия — единственная копия, `600 botkit-e2e`, вне репозитория и вне бэкапов.
4. Никаких токенов ботов на E2E-хосте.
5. Никаких паролей в файлах и в репозитории.
6. Прогон не идёт по таймеру, пока не закрыты W18 и W19.
7. Тесты не имеют побочных эффектов: проверка не пишет в production БД.

## 8. Критерии приёмки

| # | Критерий |
|---|---|
| A1 | 9/9 на стенде |
| A2 | Повторный `/start` после загрязнённого состояния даёт входной экран |
| A3 | Smoke-тест не создаёт строк в БД и не даёт `CRITICAL` |
| A4 | Негативный тест: сломанный сценарий действительно прислал оповещение |
| A5 | Watchdog присутствует: молчание теста обнаруживается |
| A6 | После прогона число строк в пользовательских таблицах не изменилось |
| A7 | `PRAGMA integrity_check` = ok во всех девяти |
| A8 | Все девять контейнеров healthy, вебхуки без ошибок |
| A9 | `botkit-e2e.timer` включается после A1–A8 |

## 9. Известные долги

1. `delivery`: при неудачном поиске заказа `return` выполняется до `state.clear()`,
   состояние не сбрасывается.
2. `smoke_all.sh`: синтетический апдейт `{"update_id": N}` пишет в production БД
   и поднимает `CRITICAL: Unhandled error`. Комментарий в скрипте о «форме,
   которую Telegram не присылает», неверен — форма валидна, обработчики
   запускаются.
3. `pricesentry.monitored_items`: нет колонки владельца, принадлежность товара
   не определить.
4. `reminder`: не найдено ни одной `CREATE TABLE` в `src`.
5. Разнобой регистрации: восемь ботов на `Command("start")`, `reminder` на
   `CommandStart()`. Поведение для `/start с аргументом` различается.
6. `E2E_ALERT_URL` пуст, Watchdog отсутствует.
